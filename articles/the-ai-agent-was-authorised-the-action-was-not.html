The AI Agent Was Authorised. The Action Was Not.

An AI agent can use a valid identity, approved tool and legitimate permission while still performing an action that nobody intended to authorise.

Enterprise security has spent decades answering one important question:

Is this identity allowed to access this system?

AI agents introduce another question.

Is this specific action appropriate for the task the agent was given?

Those questions are related.

But they are not the same.

An AI agent may possess a valid identity.

Use a legitimate access token.

Call an approved tool.

Reach an authorised system.

And still perform an action that nobody intended to approve.

The identity was valid.

The permission was real.

The tool call succeeded.

But the action was wrong.

That distinction will become increasingly important as AI moves from answering questions to changing systems.

Authentication Does Not Prove Intent

Authentication establishes identity.

Authorisation determines what that identity may access or do.

Neither automatically proves that a particular action supports the user’s intent, the agent’s assigned task or the organisation’s policy.

Consider an AI agent authorised to process employee expenses.

It may need permission to:

  • read submitted claims;
  • inspect supporting documents;
  • compare expenses against policy;
  • request additional information; and
  • approve routine reimbursements below a defined threshold.

Those permissions may be legitimate.

But suppose the agent encounters a malicious instruction hidden inside an uploaded receipt.

The instruction tells the agent to retrieve other employees’ expense records and send them to an external address.

The agent may still be authenticated.

It may still use its approved identity.

It may call tools that the organisation deliberately gave it.

Every technical access decision may succeed.

Yet the action is clearly outside the purpose of the workflow.

The agent was authorised to use the tool. It was not authorised to use it for that outcome.

Valid Credentials Can Produce Invalid Outcomes

Security systems often treat possession of valid credentials as strong evidence of legitimacy.

That assumption becomes dangerous when an AI agent can plan and execute a sequence of actions.

A human user normally chooses which application to open, which record to access and which action to perform. An agent can make those intermediate decisions independently.

It may select a tool.

Construct the parameters.

Interpret the result.

Call another system.

And continue until it believes the objective has been completed.

If the agent’s context is manipulated, its objective drifts or the model is compromised, valid credentials may simply allow the wrong plan to progress more efficiently.

This is why the discussion in The Real Risk of AI Coding Agents Is Not Intelligence. It Is Permission. remains important.

Intelligence determines what the agent can understand.

Permission determines what its decisions can affect.

But permission alone is not the end of the control problem.

The organisation must also decide whether each proposed action is appropriate at that moment, for that task and under that authority.

An Agent Needs Its Own Identity

The first architectural requirement is clear.

An AI agent should not silently inherit all the access of the person using it.

Microsoft’s guidance on securing agentic systems recommends that agents receive their own identities and task-scoped authority rather than automatically operating with the employee’s standing access.

That separation matters.

If an employee can access payroll, customer records, source code and production systems, it does not follow that every AI agent assisting that employee should receive the same access.

The employee’s authority belongs to the employee.

The agent should receive only the authority required for its approved function.

A distinct identity makes it possible to determine:

  • which agent performed the action;
  • which permissions were active;
  • which user or process initiated the task;
  • whether the agent acted independently or on someone’s behalf;
  • what systems and data were reached; and
  • how access can be revoked without disrupting the user.

Without a separate identity, accountability becomes blurred.

The audit log may show that a valid employee account performed an action, even though the decision and execution came from an autonomous agent.

That is not meaningful traceability.

It is identity ambiguity.

Least Privilege Is Necessary, But Not Sufficient

Least privilege remains essential.

An agent should receive only the permissions required for its task.

But even a minimally privileged agent may cause harm if it has excessive autonomy within those permissions.

An email agent may be legitimately authorised to send messages.

That does not mean it should send sensitive information to any recipient it selects.

A document agent may be authorised to read a repository.

That does not mean it should retrieve every file when one document would satisfy the request.

A service-management agent may be authorised to close tickets.

That does not mean it should close hundreds of alerts because it incorrectly classified them as duplicates.

A cloud-remediation agent may be authorised to change configurations.

That does not mean every technically valid change should be executed without independent verification.

Microsoft describes this distinction as applying least agency, not only least privilege. OWASP guidance similarly recommends independent tool-level authorisation and explicit confirmation for high-risk actions.

Least privilege constrains the resources an agent can reach.

Least agency constrains how independently it can act upon them.

Organisations need both.

Authorisation Must Exist At The Action Layer

Traditional access control often operates at the resource level.

Can this identity access the database?

Can it invoke this API?

Can it use this administrative function?

Agentic systems require more granular questions.

Can this agent perform this action:

  • for this user;
  • against this resource;
  • using this data;
  • for this stated purpose;
  • at this point in the workflow;
  • with these parameters;
  • under the current risk conditions?

An agent authorised to issue refunds may be limited to a particular value.

An agent permitted to create accounts may be prohibited from assigning privileged roles.

An agent allowed to send email may be restricted to approved recipients or prevented from attaching classified information.

An agent authorised to modify infrastructure may still require approval before deleting resources or changing security policies.

This is contextual authorisation.

The decision is not based only on who the agent is.

It also considers what the agent is attempting, why it is attempting it and what the potential impact would be.

The Tool Must Not Trust The Model’s Decision

A dangerous architecture allows the model to decide whether its own action is permitted.

The model reasons that a tool call is necessary.

The model constructs the request.

The model confirms that the request supports the objective.

The tool then executes it without an independent control.

The same component is effectively proposing, approving and initiating the action.

That is not separation of duties.

Every consequential tool call should pass through an enforcement layer outside the model.

That layer should validate:

  • the agent’s identity;
  • the active role and permission scope;
  • the user or business process represented;
  • the approved task;
  • the requested action and parameters;
  • the sensitivity of the affected data;
  • the destination of any information;
  • the action’s reversibility; and
  • whether additional approval is required.

The model may recommend the action.

It should not be the final authority on whether the action is allowed.

This reinforces the argument in AI Agents Need Security Boundaries, Not Just Safety Guardrails.

Guardrails influence the agent’s decisions.

Authorisation boundaries control whether those decisions become real-world actions.

High-Impact Actions Need Deliberate Friction

Human approval is sometimes presented as a temporary limitation that organisations should remove once AI becomes more capable.

That misunderstands its purpose.

For high-impact actions, approval is not necessarily a sign that the AI is immature.

It is a governance boundary.

Some actions deserve deliberate friction:

  • transferring money;
  • deleting information;
  • changing privileged access;
  • publishing external communications;
  • modifying production infrastructure;
  • exporting sensitive data;
  • disabling security controls; and
  • making irreversible business decisions.

The approval must also be meaningful.

A human should see what the agent intends to do, which resources will be affected, why the action is recommended and what evidence supports it.

A generic “approve” button attached to an opaque workflow creates the appearance of oversight without informed decision-making.

The objective is not to place a human inside every low-risk process.

It is to ensure that consequential authority is not silently delegated through convenience.

Combined Permissions Create Hidden Authority

An agent may have several permissions that appear reasonable when reviewed separately.

Read email.

Access documents.

Create tickets.

Query a database.

Send notifications.

Individually, none may appear especially dangerous.

Together, they may allow the agent to locate sensitive information, correlate it across systems and transmit it externally.

This is the agentic version of toxic access combinations.

The effective authority of an AI agent is not represented by its most powerful individual permission.

It is determined by what the agent can achieve by chaining all available permissions, tools and data sources.

Access reviews must therefore evaluate complete workflows.

What can the agent accomplish when its capabilities are combined?

Can a read permission in one system become the input to a write action in another?

Can one agent ask a more privileged agent to perform an action on its behalf?

Can information from an untrusted source influence a tool with business impact?

The architecture must assess the action chain, not merely the individual connection.

Logging Must Explain More Than What Happened

Traditional logs may show that an API call succeeded.

That is no longer enough.

When an AI agent acts, the organisation should be able to reconstruct:

  • which agent initiated the action;
  • which user or process requested the task;
  • what objective the agent was pursuing;
  • which model and agent version were involved;
  • what tools were called;
  • which permissions were active;
  • what information influenced the decision;
  • whether approval was required and who provided it;
  • what changed in the target system; and
  • how the action can be reversed.

This does not require recording unrestricted sensitive reasoning or exposing protected data.

It requires enough structured evidence to understand the relationship between the request, authority, decision and outcome.

Without that evidence, incident responders may know that something changed but not why the agent believed the change was appropriate.

Accountability requires more than attribution.

It requires decision context.

Authorisation Must Be Revocable At Machine Speed

AI agents operate faster than traditional governance processes.

A permission review next quarter will not contain an agent that is currently executing the wrong workflow.

The organisation needs the ability to:

  • suspend the agent’s identity;
  • invalidate its active tokens;
  • remove tool access;
  • block outbound connections;
  • stop running workflows;
  • isolate the execution environment; and
  • reverse or compensate for completed actions.

This is why Every AI Use Case Should Have an Owner, a Boundary and a Kill Switch is not simply a governance principle.

It is an operational requirement.

If an agent can act at machine speed, the ability to revoke its authority must operate at comparable speed.

The Architecture Must Separate Intelligence From Authority

AI models are becoming increasingly capable.

They can interpret complex requests, reason across multiple systems and construct plans that would previously have required a human operator.

But intelligence should not automatically create authority.

A model may determine that an action is useful.

A policy engine should determine whether it is permitted.

A workflow may determine whether additional approval is required.

A security boundary should determine which systems can be reached.

An independent monitoring layer should determine whether actual behaviour remains consistent with the approved task.

That separation allows organisations to benefit from capable AI without assuming that every model decision should become an enterprise action.

The agent can remain intelligent.

The architecture remains authoritative.

Final Thoughts

The next generation of security incidents may not always involve stolen credentials or bypassed access controls.

Sometimes the identity will be valid.

The token will be current.

The tool will be approved.

The API request will satisfy every technical policy.

And the outcome will still be wrong.

That is why enterprise AI security cannot stop at asking whether an agent is authorised.

It must ask:

Authorised to do what, for whom, for what purpose, under which conditions and with whose approval?

Give every agent its own identity.

Apply least privilege and least agency.

Authorise consequential actions independently.

Evaluate combined capabilities.

Preserve decision context.

Require meaningful approval where impact justifies it.

And make authority immediately revocable.

Because a valid identity does not make every decision legitimate.

A successful tool call does not make every outcome acceptable.

The AI agent was authorised.

The action was not.

Question assumptions. Share knowledge. Build trust.
